# Handoff: where Hearsay stands and every road out

**Repository:** `https://github.com/alekpeed/chord` · **Branch:** `main` · **Written at:** `e0634ea`

This supersedes `handoff-recognizer-2026-08-10.md` entirely and the forward half of
`plan-recognizer-accuracy.md`. Read this one first.

Claims are labeled **measured** (observed, with the number), **verified** (read in the code, with
the location), or **hypothesis** (plausible, unmeasured, must not be believed yet). That labeling
is not decoration: this project has repeatedly mistaken a plausible story for a result, and every
week that happened was a week spent tuning against nothing.

---

## 1. The one fact that matters

**The analyzer's accuracy on real music has never been measured.** Not once, not on any song, at
any point in the project's life.

Everything claimed as an improvement was measured against *proxy* metrics on a *single* recording:
chord count per minute, the share of symbols carrying color, and where chord changes fall in the
bar. Those say a chart is shaped like a real chart. None of them says a chord is right. The owner
tested the current build by ear and reported fewer chords and the same wrong tonality — which is
exactly what proxy metrics cannot detect, and it is the only end-to-end result the project has.

Everything in section 5 is downstream of fixing this. Nothing else should be attempted first.

**Since this was written**, the measurement loop of 5.0 has been built and run (see 5.0 and 8).
The sentence above still stands as written — synthesized isolated chords are not real music — but
"never measured on anything" is no longer true, and the machinery to measure a change is now one
command.

### The capture corpus — the current bet

844 prompts, about an hour of playing. The app names a chord, a voicing, an inversion and a
register, prints the notes lowest-first, and **only writes a take whose keys match what it asked
for**. Labels are therefore correct by construction rather than by trust.

Weighting is deliberate: over half the curriculum (inversions, voicings, register, ambiguous pairs)
exists to test the bass, because that is where the analyzer is believed weakest. The ambiguous
block records pairs built from identical notes — `Cm7`/`Eb6`, `Cm7b5`/`Ebm6`, `Cdim7`/`Ebdim7`,
`Caug`/`Eaug`, `Csus2`/`Gsus4` — where nothing above the bass can name the chord at all. The melody
block records a non-chord tone held above the chord and labels the chord *without* it, which is the
case that produced this app's worst symbols.

No audio is recorded. MIDI is both the label and the source; audio gets rendered from it through
soundfonts, so one take becomes many timbres.

**Now built:** the renderer (`training/render_takes.py`) and the harness that runs the analyzer
over the rendered audio and scores it (`training/measure_capture.py`). See 5.0.

## 3. The structural diagnosis

Two findings, both **verified** in the code, that explain more than any threshold does.

**The chromagram de-weights the bass by three to five times.** `Chromagram.kt` applies a Gaussian
in log-frequency centered at `BandCenterFrequency = 293.66` Hz — D4, above the bass register
entirely. Running the weight function: a bass note at G1 gets 0.20, at G2 it gets 0.55, while a
voicing sitting between D4 and C5 gets 0.85 to 1.0. The instrument that defines the tonal center is
the quietest thing in the representation.

**There is a working bass detector that the recognizer never sees.** `BassTracker`
(`core/audio/.../structure/SectionDetector.kt:171`) runs a genuine low-pass and produces bass notes
per beat. They are computed at `AudioAnalyzer.kt:215`, stored on the result at line 249, and
consumed by nothing. Every bass rule in the recognizer — the foreign-bass penalty, the
persistent-bass root view, `promoteBassRootedSeventh` — infers the bass from the D4-centered chroma
instead.

**Hypothesis** (explicitly not measured): these two together are why rootless voicings get named
after the upper structure rather than the bass. Plausible, mechanically consistent, and exactly the
kind of story this project has believed too easily before. The corpus is what settles it.

A third, more fundamental point: a 12-bin chromagram folds every octave into one vector, so the
bass note and a melody note occupy the same bin *by construction*. Every bass fix so far has been
an attempt to recover information the first processing step deliberately destroys.

## 4. Dead ends — measured, do not re-run

| Attempt | Result |
|---|---|
| Overtone suppression by scalar | Swept end to end. Every value fails somewhere: a phantom fifth and a played fifth land in the same bin. Needs deconvolution or a learned front end, not a constant. |
| Demucs stem separation | Color accuracy got **worse** (59% → 62–64% wrong). |
| Center-pan vocal removal | Also worse, same measurement. |
| Raising enricher floors to mask overtones | Killed legitimate tensions, kept the phantoms. Reverted. |
| Hard "beat 1 and 3 only" chord gate | Would have deleted 51% of chords when the histogram was near-uniform. |
| Three downbeat "feed-in" attempts | All reverted; one inverted the result 0/9. The real cause was scale mismatch, fixed later. |
| Public annotation corpora (Isophonics, McGill, JAAH) | Keyed to commercial recordings the owner does not have. Title-matching audio to annotations produced false positives and was abandoned. |

## 5. Every road forward

Ordered by cost. Each is stated with what it would actually buy.

### 5.0 — Finish the measurement loop *(done)*

Built. `training/measure_capture.py` renders the captured MIDI to audio, writes the Harte truth
beside it, runs the desktop analyzer over it and scores the charts with `evaluate_chart.py`, in
one command. `training/render_takes.py` is the render step alone, for generating training material
rather than scoring. Both are documented in `training/README.md`; 31 tests cover the layout, the
MIDI writer and the synthesizer.

Two design decisions are load-bearing and should not be undone casually. A take's truth span runs
from its **last onset to its first release** — the window where every note sounds at once — because
a rolled chord is not yet the chord during the roll and has stopped being it once a key comes up.
And a chord this vocabulary cannot spell is **excluded and counted by take id**, never
approximated: Harte's `5` shorthand reads back as `maj`, so writing a power chord into a truth file
would hand the analyzer a major third the player never played.

**Measured, on a machine-generated stand-in corpus** — 273 isolated chords, correct pitch sets per
quality with randomized inversions, velocities and roll, rendered through the FluidR3 General MIDI
piano, balanced profile:

| Tier | |
|---|---|
| root | 48.0% |
| thirds | 39.5% |
| sevenths | 27.7% |
| exact | 19.9% |
| boundary F | 58.0% (150 ms) |

**Read that with its caveats and no others.** It is the plumbing working, not the project's
accuracy. The corpus was generated to exercise the loop, not played by anyone; the owner's real
`takes.jsonl` has not been through it yet, and that run is the one that counts. Re-run it before
quoting any number.

What the failures look like is more useful than the number, and it is **consistent with the
hypothesis in section 3** without yet confirming it: the wrong answers are largely
upper-structure names for the chord that was played — a C major triad read as `D:hdim7`, a C7 read
as `E:min7` — and the analyzer merges several distinct chords into one long span (one predicted
`C:dom7` covered 6.5 seconds spanning three different truth chords). That is what a recognizer
naming chords from treble-weighted chroma would produce. 5.1 is the experiment that settles it,
and now it can be scored before and after.

**Known limit, unchanged:** synthesized piano has no drums, no bass guitar, no vocals, no room, no
mix compression, and isolated chords exercise identification but not the decoder. This measures the
easy case. A good score here does **not** mean the app works on records — but a bad score here
localizes the fault immediately.

There is a second limit worth naming, and it turned out to be bigger than expected. The renderer's
built-in additive synthesizer — the fallback when no soundfont is installed — is not merely less
realistic than a piano, it is **much harder**: on the same corpus through the same analyzer it
scored 3% root where the soundfont scored 48%. That is a measured 16× gap between two renderings
of identical MIDI, and it is worth remembering as a caution about how sensitive this front end is
to timbre. Anything measured on one instrument is a claim about that instrument.

So install the soundfont (`sudo apt install fluidsynth fluid-soundfont-gm`). The default backend
is `auto`, which uses it whenever it is present and falls back otherwise; the backend that
actually ran is written into `measurement.json` and printed in every summary, so a score cannot be
quoted without it.

### 5.1 — Wire the bass detector to the root

`BassTracker` exists and feeds nothing. Make the root come from detected bass notes rather than
from treble-weighted chroma energy. Small, reversible, and it directly attacks the failure the
owner keeps reporting. Cheap enough to be worth doing on the strength of the hypothesis alone —
but score it before and after, or it joins the list of changes nobody can evaluate.

Scoring it is now two commands, so there is no excuse for skipping them:

```
python3 training/measure_capture.py --takes ~/hearsay-capture/takes.jsonl \
    --out data/before --backend fluidsynth --label "before BassTracker"
# make the change, then ./gradlew :tools:analyzer:installDist and run it again into data/after
```

The inversions, voicings and ambiguous blocks are over half the curriculum precisely because they
are where this change should show up. If root accuracy on those blocks does not move, the
hypothesis in section 3 is wrong and the next thing to try is 5.2.

### 5.2 — NNLS chroma front end

Replace the STFT-fold with a constant-Q transform and solve for which fundamentals explain the
spectrum, via non-negative least squares against a dictionary of harmonic combs (the Mauch & Dixon
approach behind Chordino). Roughly two sessions. No training data needed. Kills the overtone
problem that no scalar could, and yields separate bass and treble chroma as a natural product
rather than as a weighting hack. The rest of the pipeline survives unchanged.

### 5.3 — Note transcription, then symbolic chord inference

Run a polyphonic transcription model (Spotify's `basic-pitch` is the obvious candidate: small,
open, ONNX-exportable) to get actual notes with pitch and time, then infer chords from the note
list. This is a rewrite of the front half of the analyzer.

Highest ceiling of the unlearned options, and the only one that makes the app *inspectable*: it can
show the notes it heard, so a wrong chord becomes a visible disagreement rather than an argument
with a black box. It also matches how the owner reasons — every complaint from them has been
note-level ("a G minor where I never hear a B-flat"). Corrections would become note-level too,
which is far better training data than chord labels.

Cost: a new model dependency, ONNX Runtime on device, and `docs/model-registry.md` governs — no
model ships without benchmarked memory and runtime on real hardware, a defined fallback, and a
visible quality classification.

### 5.4 — Learned chord classifier

A CNN or CRNN over CQT producing chord posteriors per frame. What the field has done since roughly
2016 and what Chordify does. Highest ceiling overall.

Previously written off as blocked on training data. **That was too quick.** The capture corpus is
the unblock: labeled audio can be generated without owning a single commercial recording, by
playing chords and by rendering MIDI through soundfonts with augmentation (reverb, EQ, noise,
mixing against drum and bass stems). 844 musical examples is thin for training from scratch and
adequate for fine-tuning a pretrained model; more playing sessions extend it at a known cost per
hour.

**The honest gap:** synthetic and solo-piano audio will not teach a model to handle a dense mix.
Closing that needs either real multi-track material or a model pretrained on it.

### 5.5 — Narrow the product instead

If measurement shows the front end cannot be made accurate at acceptable cost, the app can be
honest about what it *can* do: bass and root movement, which is the most reliable signal it
produces and the thing the owner has said matters most. A tool that reliably gives you the roots
and lets you fill in qualities is more useful than one that confidently invents `Bbmaj9`.

### 5.6 — Stop

A legitimate outcome, and cheaper than a rewrite that does not work. The decision point is after
5.0: with real numbers, "is this fixable at a cost worth paying" becomes answerable instead of a
matter of morale.

## 6. Open defects

1. **Bass detector unused** — section 3. The largest known structural gap.
2. **Low-frequency resolution** — at 22 kHz with a 4096-point transform, bins are 5.4 Hz apart
   while a semitone at C3 is 7.7 Hz, so low fundamentals smear into neighboring pitch classes.
   Weighting the region harder produced phantom minor ninths on every root. Needs a longer
   transform or a CQT (see 5.2), not a weight.
3. **`MetricalHypothesisEvaluator.downbeatPhase`** — computed, never read.
4. **APK 56 BPM confirmation** — the `DecodeSink` 2× tempo fix has Robolectric tests but has never
   been confirmed on the physical tablet.
5. **Corrections exporter** — the database is verified training-ready (`ChordEventEntity` →
   `RevisionEntity` → `MediaAssetEntity`, with `MACHINE`/`USER` provenance and `userConfirmed`),
   but nothing exports user corrections to Harte `.lab`. That is the other route to real-recording
   ground truth, and it needs the owner to correct songs by hand.

## 7. Working practices this project learned the hard way

- **Nothing executes without an explicit instruction.** A question is a question.
- **Never tune against one recording.** Everything measured that way this week failed to generalize.
- **Never invent the ground truth.** When a chord is reported wrong, the right chord is not
  something to deduce and then explain — that is fabrication with a mechanism attached.
- **One build lock, one agent.** Parallel agents sharing a Gradle project livelock: each one's
  `clean` destroys the other's in-flight run.
- **American English everywhere.** `JobStatus.CANCELLED` and `AnalysisFailure.Cancelled` are
  deliberate and are written into the `analysis_jobs` table as literal strings.

## 8. Running things

```
./gradlew test detekt                          # everything
./gradlew :app:assembleDebug                   # tablet
./gradlew :tools:desktop:createDistributable   # desktop app
./gradlew :tools:analyzer:installDist          # the analyzer the measurement loop calls
cd training && python3 -m unittest discover tests
```

The measurement loop, which is the thing to run before and after any analyzer change:

```
sudo apt install fluidsynth fluid-soundfont-gm ffmpeg     # once
python3 training/measure_capture.py --takes ~/hearsay-capture/takes.jsonl \
    --out data/measure --backend fluidsynth --label "what changed"
```

It writes `data/measure/measurement.json`: the scores together with the backend, profile and take
counts that produced them. Two of those files are a before-and-after. Roughly a minute of analyzer
time per two-and-a-half-minute sheet on the balanced profile.

Analyzer CLI: `./tools/analyzer/build/install/analyzer/bin/analyzer <file> --profile balanced
--force --text`, which writes `<file>.hearsay.json` with full structured chords.

Capture output: `~/hearsay-capture/takes.jsonl` on desktop, the app's external files directory on
the tablet. One JSON object per line; progress resumes from the file.

CI runs on every push to `main`; the `latest-apk` release always carries the newest APK, Linux
desktop app and analyzer CLI.
